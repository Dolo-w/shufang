计算方法

多轮对话的计费陷阱在于：上下文每轮重发。第 i 轮发送的输入 = 固定前缀 + (i-1) × 每轮新增——第 20 轮时，你可能已经把同一段系统提示词发了 19 遍。整段对话总成本 = Σ(第 i 轮输入 × 折后输入价 + 第 i 轮输出 × 输出价)，再乘以每天对话数 × 30 得到月账单。

Prompt Caching 是 Agent 场景的第一杠杆：每轮重发的历史前缀里，与上一轮重复的部分可以按缓存价（原价 5%~10%）计费。用滑块调整命中率，观察账单曲线的变化——对固定前缀大、轮数多的 Agent，缓存常常砍掉一半以上账单。缓存价未公开的模型（Google、Qwen、Kimi、GLM、豆包、MiniMax）按原价保守估算，实际可能更低。

常见问题

为什么 Agent 跑得越久，账单越贵？

因为上下文每轮全量重发：第 i 轮的输入包含前 i-1 轮的所有消息和工具结果。一个 20 轮的对话，实际发送的输入 token 总量约为「末轮上下文 × 轮数 ÷ 2」——滚雪球就是从这个平方级增长来的。上下文越长，单价越高的旗舰模型账单放大越明显。

Prompt Caching 真能省一半吗？

对固定前缀大（长系统提示、大工具定义）且轮数多的 Agent，重发部分通常占总输入的 60%~90%，其中绝大部分是逐轮重复的前缀，可被缓存命中。按缓存价 5%~10% 计算，总输入成本常能降一半以上。前提是请求的前缀与上次完全一致（各家实现略有差异），且缓存有时效（如 5 分钟），间隔过久的会话可能失效。

怎么快速降低多轮对话账单？

按性价比排序：① 开 Prompt Caching（本页滑块模拟）；② 工具结果做裁剪/摘要，压住每轮新增量；③ 对历史做滚动截断，别无限带全文；④ 能用轻量模型收尾的轮次（如格式化输出）切小模型；⑤ 离线批量任务走 Batch 接口（约 5 折，见成本计算器的开关）。

上下文长度和输入 tokens 是一回事吗？

不是。上下文长度是模型单次能处理的容量上限（如 128K、256K tokens），输入 tokens 是你这一轮实际发送并计费的数量。模型支持长上下文 ≠ 便宜地用长上下文——容量是天花板，账单看的是每轮实际发送量。
